# Native identity and access control

AlacreOS places human identity, login and account administration in a native management service. Alacre Core isolates the service, authenticates its IPC peers through kernel-controlled endpoints, and enforces the capabilities granted to each protection domain. A native account role authorizes a defined management operation. Linux UIDs, GIDs and UID 0 have meaning only within their compatibility domain. Safety functions run with their own admitted resources and capabilities and continue or reach their defined safe state according to the deployment's hazard analysis when management becomes unavailable.

## Account and session core

The freestanding C++23 [directory](../services/identity/identity.hpp) implements a static account roster and a volatile session and audit store. One serialized management service owns it. Both QEMU targets boot it in an isolated guest domain. The reference host adapters exercise mutual TLS and persistent account status and audit records with the same directory implementation.

Session IDs increase within one instance. They are handles, and authorization also requires the same trusted channel and the live account role. The roster is provisioned from trusted configuration once at start. Runtime administration can enable or disable commissioned accounts. Names, enrollments, role assignments and changes to credentials belong to the provisioning and authentication layers.

The audit ring keeps events in insertion order and overwrites the oldest record on saturation. Readers can detect retained or lost history through the returned count and saturating overwrite counter. Offsets refer to the current ring contents. The ring is volatile. It also receives certificate verification rejections when the host verifier reports them. After a clock fault, service recovery and export of diagnostic evidence are the supervisor's responsibility. A disconnect processed after a clock regression records the last trusted tick. The deployment's protected audit sink must define its integrity, delivery, retention and loss handling requirements.

## Development and host profiles

The guest calls use six integers in registers and have no user pointers or shared writable pages. AArch64 uses EL0 with per-domain translations and x86-64 uses ring 3 with separate page tables and a TSS stack for traps. Client text is read-only and stacks and service state are non-executable from userspace. The bootstrap injects two fixture sessions and mediates requests. The development watchdog and IPC run after the EDF test and do not establish bounds for safety workloads. The guest itself has no login interface, credential store or persistent account storage. [Arm AArch64 memory permissions](https://documentation-service.arm.com/static/63a43e333f28e5456434e18b?token=) · [Intel system programming manuals](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)

The host verifier accepts a full TLS 1.3 server-side handshake with standard certificate verification and maps the client certificate SHA-256 fingerprint to a provisioned account. Each connection can open one session. The calling transport owns the connection and attests the channel. TLS termination, client trust configuration, certificate revocation, rate limiting and authenticator hardware are deployment responsibilities. The implementation supplies no default credentials. [OpenSSL peer verification](https://docs.openssl.org/3.0/man3/SSL_CTX_set_verify/)

The host store opens an existing database provisioned with [the schema](../services/identity/host_schema.sql). The service requires a private database directory with one writer. A status change and its audit record commit atomically before the in-memory update. A failed commit closes management access until restart from the stored roster. The sink appends other events independently and exposes a latched delivery failure. The host test covers database reopening and transaction failures. Power-loss behavior, independent audit protection and storage limits need deployment evidence. [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html)

## Runtime integration requirements

1. Launch the identity service in its own protection domain with explicit IPC, clock and storage capabilities. The adapter supplies a monotonic time and a kernel-attested channel identity bound to a peer and its channel lifetime. Serialize requests with disconnect events and wait for teardown before reusing a channel identity. On service restart, invalidate the old channels before accepting requests against the new instance.
2. Open sessions only after a trusted verifier authenticates the specific account on that channel with fresh proof. Protect the verifier and credential store, limit attempts and concurrent verification per account and interface, and record relevant verifier failures. Select authenticators for the deployment's assurance target, including phishing-resistant MFA for privileged remote access. Provision named accounts through a trusted commissioning path with no shared or default credentials. Define controlled recovery and verify that restart preserves the securely committed roster and account status.
3. Check the required role against the live session for each protected request, under the same serialization boundary as revocation. Carry out the operation through scoped capabilities. If a profile issues longer-lived capabilities or queues privileged work, it must withdraw or revalidate that authority at use and bound the handling of operations already in flight. The safety requirements specify which operations may change safety parameters and when those changes can take effect.
4. Export audit events to a protected sink with independent access and bounded buffering. Test saturated storage, delivery failures and restart while the admitted safety path operates independently of audit and identity I/O. Allocate and account for management CPU, memory and interrupt interference. Test account disablement, clock fault, service crash and authentication failure while the qualified safety workload continues or reaches its specified safe state.

## Standards and qualification

- The safety lifecycle starts with hazard analysis. The deployment assigns safety functions and integrity targets, determines the management plane's effect on each function, and traces applicable requirements through design, fault analysis, verification and assessment. [IEC 61508-3:2010](https://webstore.iec.ch/en/publication/5517)
- Industrial component security covers identification, authentication and use control. The applicable requirements and target security capability depend on the evaluated component and deployment. [IEC 62443-4-2:2019](https://webstore.iec.ch/en/publication/34421)
- Account management, access enforcement, separation of duties and least privilege map to AC-2, AC-3, AC-5 and AC-6. Remote user authentication and session management use a separate set of guidelines. [NIST SP 800-53 Rev. 5](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) · [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

The current evidence supports only the directory behaviors listed above. A conformity or SIL claim requires the deployed safety functions, selected controls, runtime integration, qualification evidence and applicable assessment to be in scope.
